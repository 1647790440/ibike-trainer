# iBike · 本地智能骑行控制台

用浏览器给智能骑行台设定训练目标，程序通过蓝牙 FTMS 协议控制骑行台把功率稳定在
目标值（ERG 模式）。不依赖 Zwift / MyWhoosh，不需要联网，不需要付费，数据全在本地。

**三种训练模式：**

- **恒定功率** —— 设定 60 分钟 / 100 瓦，骑行台自动调整阻力，让你始终踩在 100W 附近
- **间歇训练 HIIT** —— 6 个内置方案（4×4、2×20、30/15、Over-Under、Tabata…），
  强度全部按 %FTP 定义
- **自定义课程** —— 自己排小节（时长 + 功率），存成固定课程反复用
- **FTP 测试** —— 坡道 / 20 分钟 / 8 分钟三种方案，测完自动算出阈值功率并存下来

**外加心率带** —— 标准蓝牙心率带（`0x180D`）直连，实时显示心率与心率区间，
报告里给出平均/最大心率、区间分布和心率曲线，还可以开「心率上限保护」当安全刹车。
真带子到货前也能用 `./run.sh --sim` 先看一遍。

**外加训练报告** —— 每次训练结束自动保存，可以随时回看历史、逐条删除。

手机连同一个 Wi-Fi 就能操作（启动时终端会打印二维码，扫码即可）。

```
┌──────────────────────────────────────────────┐
│  本机访问 :  http://127.0.0.1:8765           │
│  手机访问 :  http://192.168.1.23:8765        │
│  [ 二维码 ]                                   │
└──────────────────────────────────────────────┘
```

## 快速开始

```bash
cd ~/Desktop/ibike
./run.sh
```

首次运行时 macOS 会弹窗询问蓝牙权限，必须允许（在
**系统设置 → 隐私与安全性 → 蓝牙** 里勾选你的终端 App，比如「终端」或「iTerm」）。
否则程序搜不到任何设备。

浏览器会自动打开控制台。

### 命令行参数

`run.sh` 会把参数透传给 `main.py`：

| 命令 | 作用 |
|---|---|
| `./run.sh` | 正常启动（连真实骑行台） |
| `./run.sh --sim` | 用模拟骑行台，不接硬件也能把完整流程走一遍 |
| `./run.sh --sim-dumb` | 模拟一台「收下目标功率但不执行」的骑行台，用来看「阶跃探测 → 确认无响应 → 自动降级」的完整过程 |
| `./run.sh --diag` | 诊断原生 ERG：把「骑行台回报的阻力档位」打出来，判明功率为什么压不到设定值 |
| `./run.sh --scan` | 扫描一次然后退出：同时列出骑行台和心率带，确认都能搜到 |
| `./run.sh --scan-timeout 15` | 扫描时长（默认 8 秒；搜不到设备时可以调长） |
| `./run.sh --port 9000` | 换端口（默认 8765） |
| `./run.sh --host 127.0.0.1` | 只监听本机（默认 `0.0.0.0`，手机也能访问） |
| `./run.sh --no-browser` | 不自动打开浏览器 |

界面分成两页，顶部导航切换：

| 页面 | 管什么 |
|---|---|
| **1 连接设备** | 把设备接上：**1. 扫描与连接**（一次扫描同时列出骑行台和心率带，点一下就连）、**2. 骑行台**（连接状态 + 实时功率/踏频/速度/阻力档位）、**3. 心率带**（连接状态 + 实时心率/区间/电极，还有电量） |
| **2 训练** | 训练目标、心率参数、实时数据、训练总结、训练报告 |

分开是因为它们对应两件不同的事——连接的时候不该被一堆训练参数淹没，
骑行的时候也不该看到设备列表。停留的页面会被记住，刷新不会跳回去。

设备页为什么要拆成三块：**扫描/连接**是一件事，**每台设备自己的状态**是另一件事。
骑行台和心率带各自有状态和实时读数，连上之后数据立刻在动，一眼就能确认连成功了；
"扫描与连接"那块只管发现设备、建立连接，连上的那台会标上「已连接」，不用再去别处找。
训练页顶部还有两枚状态胶囊（骑行台 / 心率带），因为那一页看不到这两块。

### 操作流程

1. **连接设备** —— 骑行台通电、踩两圈唤醒；心率带戴上（电极沾点水）。
   点一次「扫描蓝牙设备」，下面会同时列出骑行台和心率带，各点一下就连上了。
   骑行台那行的名字后面带 `FTMS` 标签。连过一次的设备下次会自动重连。
2. **设定目标** —— 切到「2 训练」，在四种模式里选一种，顺便核对一下心率参数
   （最大心率、区间算法）。第一次用建议先做一次 FTP 测试。
3. **开始训练** —— 一开始训练会自动切到训练页。实时显示当前功率、踏频、心率
   （和心率区间）、剩余时间、平均/最大功率、标准化功率、距离、做功。
   训练中随时可以 ±5/±10W 调整目标功率、暂停或结束。
4. **看总结** —— 点「结束」或跑满时长后自动生成总结，**同时自动存进训练报告**。
   可以「再来一次」用同样的参数重开，或「关闭」回到设置界面。

## 训练总结

点结束之后会生成一份总结。既然这套程序的核心价值是把功率压在目标上，总结里
最重要的不是"平均功率"这个数字本身，而是**这次到底控得准不准**——平均 100W
可能是一路精确的 100W，也可能是 80W 和 120W 各占一半。

**核心指标**

| 指标 | 说明 |
|---|---|
| 控功率达标率 | 功率落在目标 ±5% 内的时间占比，附带一句人话评价 |
| 平均偏差 | 功率与目标的平均绝对偏差（W），比"平均功率"更能反映控制质量 |
| 实际比目标 | 平均功率相对目标的偏移量，±5% 内显示为绿色 |

**其余数据**：平均/最大/标准化功率、平均/最高踏频、做功（kJ）、估算消耗（kcal，
按 23% 做功效率折算，页面上会写明这个假设）、距离、实际时长与计划时长、起止时间、
控功率方式。

**功率区间分布**：按目标功率的百分比分 5 档（低于 90% / 90–97% / 97–103% /
103–110% / 高于 110%）统计停留时间，一眼能看出是偏软还是偏硬。

**整段功率曲线**：和实时界面同款，目标功率画成阶梯虚线，所以训练中途改过目标
也能如实反映。曲线点做了压缩（每个分桶保留最小值和最大值，而不是简单抽点——
抽点会把短暂的功率尖峰整个丢掉，而尖峰恰恰是看训练质量时最该保留的）。

间歇训练还会额外给出**分段明细**表：每段的目标、实际平均功率、达标率，让
你一眼看出是哪一组踩崩了。整体平均会把踩崩的第 3 组和踩得漂亮的第 5 组平均掉，
看不出问题在哪。

一个细节：**训练不足 60 秒时不显示标准化功率**。NP 建立在 30 秒滑动窗口上，
数据太短时窗口只增不减，早期爬升段会被严重放大，算出来的 NP 甚至可能低于
平均功率——那是个误导人的数字，不如不显示。

## 心率带

程序可以同时接**两根**蓝牙设备：骑行台和一根标准心率带（任何走蓝牙心率服务
`0x180D` 的都行：迈金、Polar H10、Wahoo TICKR、Coospo……）。它们互不相干，
只连一根也能正常训练。

```
1. 进「连接设备」页
   点一次「扫描蓝牙设备」——骑行台和心率带是同一次扫描里一起找出来的，
   下面分成两块列出，各点一下就连上（顺序随意，先连哪个都行）
2. 连过一次会记住地址，下次启动自动重连
```

**它能做什么**

| | 说明 |
|---|---|
| 实时心率 + 电量 | 界面显示 bpm、当前心率区间和带子电量 |
| 心率区间分布 | 训练报告里给出 5 个区间的停留时间，和功率区间并排 |
| 心率曲线 | 和功率画在同一张图上（双刻度）——"同样的功率、心率一路往上爬"只有叠着看才看得出来 |
| 心率上限保护 | 可选。超过设定心率并持续 10 秒就自动把目标下调 5%，最多降到本段的 80%；心率回落后再回到原计划 |

**区间怎么算**：设置里选「按最大心率百分比」或「按储备心率（Karvonen，更准）」。
后者需要静息心率——它把"你躺着时的心率"当作真正的零点，同样跑 150bpm，
静息 50 的人比静息 70 的人轻松得多，前者算得更准。

**心率上限保护是一道刹车，不是控制方式。** 心率本身滞后 30~60 秒，拿它做闭环
一定会振荡，所以程序不会去"追"心率，而是分几步往下让。自由骑行模式下程序本来
就不控制功率，这时只提示、不改功率。

**心率数据会自动判活。** 心率带是独立设备，会飘出范围、会没电、会被手机抢走。
超过 10 秒没收到数据就不再显示冻结值（界面写「未收到数据」），报告里也只统计
真正采到的那段时间——和功率那条链路的处理是一致的。

**顺带会告诉你这根带子支不支持 RR 间期。** 标准心率帧里除了 bpm 还可能带
RR 间期（逐拍间隔），有它才能算 HRV。程序现在只把它记下来（训练报告里会写），
不做 HRV 计算——那需要静息条件下单独采集，属于另一个功能。

### 关于"骑行台自带心率"

FTMS 的 Indoor Bike Data 里本来就有个心率字段，程序一直会解析它。但那条路只在
骑行台自己带心率传感器时才有数据（少数动感单车是这样）。所以心率有两个来源，
程序按"独立心率带优先"取数。

## 训练报告

**每次训练结束都会自动保存一份报告**，不需要手动点什么。在设置界面下方能看到
「训练报告」列表，按时间倒序排列，每一条显示方案名、**开始时间**、时长、
平均/目标功率、NP、做功——够你认出"这是哪一次"。点开就能看到和刚骑完时一模一样的
完整总结（达标率、功率区间分布、整段功率曲线、间歇训练还有分段明细）。

点条目右侧的 `×` 删除单份报告，右上角「清空全部」清空所有记录。删除前都会确认。

报告存在 `data/reports/` 下，**一次训练一个文件**，纯文本 JSON，可以直接备份。
之所以不是把所有报告塞进一个大文件：报告只增不减，单文件方案每存一次都要重写
全部历史，数据量一大就慢，而且写坏一次全部丢失。写入同样走"临时文件 + 原子替换"。

几个实现上的细节：

- **上限 500 份**（每份含曲线约 30KB，合计约 15MB）。超出后删除最旧的，并在日志里
  明确记一条——不静默丢用户数据。想保留更久可以定期把 `data/reports/` 备份走。
- **报告 id 来自客户端，所以做了白名单校验**。`GET /api/reports/<id>` 里的 id
  只允许字母数字和 `-`/`_`，解析完还要确认结果仍在报告目录内——两道保险挡住
  `../` 这类目录穿越。
- **列表接口不返回功率曲线**。列表只需要几个数字，没必要把几十 KB 的轨迹也传一遍。
- 目录里混进坏文件或不相关文件时，会被跳过并记日志，不会让整个列表打不开。
- 报告里保留**功率、目标、阻力和踏频**四列轨迹。阻力和踏频是有意留着的——
  报告是事后复盘问题的唯一依据，把这两列丢掉的话，"阻力为什么突然变了"
  这类问题就完全无从查起（真的遇到过）。
- 报告里还记录**控功率方式的切换**（什么时候、从什么切到什么、为什么）。

### 想先看看效果？可以生成示例报告

没接骑行台、或者暂时没时间真骑的时候，可以生成几份**合成报告**来预览界面：

```bash
.venv/bin/python tools/make_sample_reports.py           # 生成 7 份示例报告
.venv/bin/python tools/make_sample_reports.py --clear   # 删掉示例报告和示例课程
```

这些报告是模拟出来的，但**格式和真实训练完全一致**：功率曲线用一阶惯性模型模拟
ERG 的实际响应（起步爬升、飞轮滞后、稳态小幅波动），闭环阻力那份还复刻了真实的
控制律（每 4 秒按误差修正阻力档位），然后走真实的总结计算逻辑得出达标率、区间
分布、分段明细和降采样曲线。所以界面上看到的就是真东西，不是手写的假数据。

示例里覆盖了恒定功率、4×4、2×20、30/15、Over-Under（闭环阻力模式）、中途放弃、
以及一门自定义课程，时间散布在最近十来天。

这些报告都带一个 **「示例」角标**，一眼能分辨出不是真实训练记录；重复运行脚本会
先清掉上次生成的示例、不会越攒越多。顺带会创建一门叫「示例课程 · 周末耐力」的
自定义课程，好让那份报告的「再来一次」能真正复现。

`--clear` **只删带示例标记的数据**，你真实训练产生的报告一份都不会动——想删那些，
请在界面上逐条删或点「清空全部」。

## 控功率的两条路径

程序会优先尝试**原生 ERG**，不行就自动退到**闭环阻力**。这是为了兼容那些
FTMS 实现不完整的固件。

| 方式 | 原理 | 特点 |
|---|---|---|
| **原生 ERG** | 下发 `Set Target Power (0x05)`，骑行台固件自己闭环调阻力 | 响应快、手感好，和 Zwift 一样。需要固件真正支持 |
| **闭环阻力** | 只下发 `Set Target Resistance Level (0x04)`，本程序读回实际功率，用自适应控制器不断修正档位 | 兼容性最好。响应稍慢，但能把功率控住 |

闭环控制器建立在「功率 ≈ 系数 × 阻力档位 × 踏频」这个近似上，并在骑行过程中
**在线辨识**那个系数：

```
k ← (1-α)·k + α·(P / (R·C))
ΔR = β · (P目标 - P实测) / (k · C)
```

用辨识出的 `k` 归一化意味着**踏频变化会被自动补偿**——踏频掉了，阻力会自动补上，
这正是 ERG 该有的手感。踏频低于 25rpm 时控制器会暂停调整，免得你重新踩起来时
阻力大得踩不动。

两个抗振荡的细节（少了它们功率会来回冲）：β 取 0.55 而不是 1，每步只修正一部分
误差；而且只在阻力稳定下来之后才去辨识 `k`，不拿过渡过程的数据去污染模型。
实测调整前后：

| | 稳态功率区间 | 峰峰值 |
|---|---|---|
| 一次修正到位（β=1，2 秒一调） | 78 ~ 119 W | 41 W |
| **现在的参数**（β=0.55，4 秒一调） | **95 ~ 104 W** | **9 W** |

闭环控制的起始档位取的是**骑行台当前实际所在的档位**，而不是量程的中间值。
这一点很重要：无论从原生 ERG 切过来、还是暂停之后继续，阻力都从原地接手。
早期版本固定从"量程的四分之一"起步，于是每次切入都会先掉一大截再慢慢爬回来——
实测过一次 1 小时 130W 的训练，阻力从 17 掉到 6、花了一分多钟才爬回 17，
就是这个问题。

「自动」模式还有一个保护：如果骑行台声明支持目标功率、但实际压根不理会
（收下指令回 Success，功率却纹丝不动），程序会识别出来并**自动切换到闭环阻力
控制**，同时在日志里提示。判定分两步——先**立案**（功率很稳、但稳定地偏离目标），
再**取证**（做一次目标功率阶跃探测）：

```
1. 立案：连续 18 秒功率都在 ±max(8W, 目标 6%) 容差带之外，且标准差 < 8W
2. 取证：临时把目标功率往下压 25W，观察 20 秒
   ├─ 功率跟着往下走 ≥ 8W  → 固件确实在响应，保留原生 ERG，3 分钟内不再打扰它
   └─ 功率纹丝不动         → 实证固件不响应，才切换到闭环阻力
```

**为什么第二步不能省**：功率稳、却稳定偏离目标，光凭这一条是分不清
"固件装死"和"固件在跟、只是整定有偏差"的。动感单车的功率常常是固件用
「阻力 × 踏频」算出来的，骑手踏频一稳，功率就能稳得毫无波动，看起来像固件
不理人，其实它正在慢慢把阻力加回去。真机上就踩过这个坑：一次 60 分钟 130W 的
骑行，功率平稳地掉到 114W 并保持了一分多钟，程序据此判成"固件装死"就把控制权
切走了——而用户明明选的是 `auto`（本意就是"用原生 ERG"）。切换的代价很大
（控制权整个易手，骑手能立刻感到阻力跳变），所以现在宁可先花 20 秒取证。

**明确选了「原生 ERG」就绝不自动切换。** 自动降级只是 `auto` 模式为了兼容性
兜的底，不该反过来覆盖用户的明确选择。

**但 FTP 测试期间不做这个降级判断。** 坡道测试每级都在抬高目标，功率本来就滞后几秒，
正好落进"稳但偏"的判据里；一旦降级成闭环阻力，阻力被锁死，坡道就再也加不上去，
整个测试就废了。同理，普通课表换段之后也会把观察窗口清零，重新给固件一次机会——
否则换段频繁的间歇课表也可能被误判。

## 诊断：为什么功率压不到设定值

如果骑行台声明支持目标功率，功率却长期压不到设定值，别猜——跑一次诊断：

```bash
./run.sh --diag              # 约 4 分钟，全程保持踩踏
./run.sh --diag --sim        # 没有硬件时先看一眼输出长什么样
./run.sh --diag --quick      # 每个阶段 30 秒
```

它比训练报告多给出一列关键数据：**骑行台自己回报的阻力档位**。原生 ERG 模式下
程序一个阻力指令都没发过，所以这一列完全是固件的行为，也正是回答
"它到底有没有在调阻力"的唯一直接证据。诊断跑三个对照阶段：

| 阶段 | 做什么 | 用来排除什么 |
|---|---|---|
| **A** | 原生 ERG + 每 2 秒重发目标功率（程序现在的做法） | 基准 |
| **B** | 原生 ERG + 只在开头发一次 | 每 2 秒重发会不会打断固件自己的积分器 |
| **C** | 目标功率 +40W / −40W 阶跃 | 固件对"设定值"到底有没有伺服能力 |

跑完直接给结论，四种可能：

1. **阻力档位一动不动、功率又稳又偏** → 固件的"原生 ERG"是开环的，`Set Target Power`
   只是"把瓦数换算成一次阻力档位就完事"。**用闭环阻力。**
2. **阻力在动、功率却停不下来** → 固件有闭环，但内部伺服的量和它上报给你的功率
   不是同一个数（刻度/零点偏差）或死区太大。**用闭环阻力更准**，程序按你读到的功率伺服，
   正好把偏差补掉。
3. **阶段 B 明显比阶段 A 好** → 每 2 秒重发一次把固件的积分器打断了。把
   `POWER_KEEPALIVE_S` 放宽到 30~60 秒。
4. **功率稳在目标附近** → 原生 ERG 是好的，训练中被降级多半是骑手自己骑低了或数据
   链路卡了一下。

### 这个诊断是怎么来的

一次真实的 60 分钟 130W 骑行里，功率在 t≈912~930 秒整整一段**每一个采样点都精确等于
114W**——而目标是 130W。人的腿不可能这么稳，所以那几秒里骑行台报的功率必然是它自己
用「阻力 × 踏频」算出来的固定值：**阻力没动，功率就没动**。

再看全程，这种"12 秒完全不动"的平台在原生 ERG 段占 22%，平台值散布在 76 / 114 / 116 /
118 / 119 / 124 / 126 / 129 / 131 / 134 / 163 W——**一个真正在闭环的 ERG 不可能让功率
稳定地停在偏离目标 30W 的地方**。也就是说：它报的"支持目标功率"是个声明，不是保证。

区别只在于"它为什么不动"（开环查表 / 死区太大 / 刻度偏差 / 重发打断积分），
一小时的功率曲线分不出来——缺的就是**回报的阻力档位**那一列。所以有了这个脚本。
另外训练报告的曲线从这一版起也会保存 `res`（阻力）和 `cadence`（踏频）两列，
以后复盘不必再靠猜。

## FTP 测试

FTP（功能阈值功率）是这套程序里其他一切强度的基准——HIIT 方案的 %FTP、自定义课程的
百分比，全都换算自它。所以先把它测准，比什么都重要。

切到「FTP 测试」标签，选方案、改参数、看课表预览，然后开始。**测完会算出 FTP 并给出
「用这个 FTP」按钮**，点一下就存下来（跨重启保留），后面的课表自动按新值折算。

### 三种方案，以及一个关键的技术点

| 方案 | 控制方式 | FTP 怎么算 | 特点 |
|---|---|---|---|
| **坡道测试** | **ERG** 自动加载 | 最好 1 分钟功率 × **75%** | 不需要配速技巧，全程自动，程序会识别力竭 |
| **20 分钟测试** | **自由骑行** | 计时段平均功率 × **95%** | Allen-Coggan 标准方案 |
| **8 分钟测试** | **自由骑行** | 较好一次平均功率 × **90%** | 比 20 分钟轻松一些 |

**那个关键点：20 分钟和 8 分钟测试绝不能用 ERG。**

ERG 会把功率锁死在你设定的值上。而测试的目的恰恰是找出你能骑多高——如果用 ERG，
你测出来的是「你事先设定的那个数」，不是你的能力，整个测试就废了。所以这两种方案
走的是**自由骑行**模式：程序设一次阻力就撒手，功率完全由你配速（界面上可以微调阻力，
骑行台上能调的就只有它和踏频）。

坡道测试则相反：它必须用 ERG，因为要由骑行台逐级往上加负荷。这个区别不是可选项，
所以**控制方式由方案决定，不接受前端指定**——服务端会强制覆盖。

### 20 分钟测试里那个容易被忽略的 5 分钟

Allen-Coggan 的原始方案里，20 分钟计时**之前**有一次 5 分钟全力。很多人把它当热身
跳过了，但它是有明确目的的：**先把无氧储备耗掉**。

不这么做的话，20 分钟里前几分钟靠无氧供能撑出来的那部分功率会让平均值虚高，算出来的
FTP 比真实阈值高。Coggan 和 Allen 在原始方案里写得很清楚，所以本程序把它做成了
固定环节。

另外那个 95% 也只是**人群平均**：原文明确说了，无氧能力天生强的人需要减掉更多，
弱的人可能只需要减 3%。所以别把这个数当成精确的生理量。

### 坡道测试怎么判断"踩不动了"

不需要你手动按结束。程序盯着两件事，命中任一条并持续一小段时间就判定力竭：

- 5 秒平均功率掉到目标的 **80%** 以下（持续 5 秒）
- 踏频掉到 **50rpm** 以下（持续 3 秒）

换级之后的前 6 秒是宽限期——那几秒功率还在往上爬，不算数。

**还有一个防呆**：如果你把全部级数都踩完了却依然没力竭，说明坡道设得太短，这时结果会被
标记为**无效**并提示"把递增调小或级数调多再测"，而不是给出一个看着挺正经、其实毫无意义
的数字。少于 3 级的结果同样无效。

### 关于"职业车队怎么做"

查了一圈公开资料，结论可能和直觉相反：**WorldTour 车队很少做这种室内的单一 FTP 测试。**

他们主要靠：

- **血乳酸测试**——逐级加载、采指血，找 LT1 / LT2 拐点（常以 2 mmol/L、4 mmol/L
  或 Dmax 法判定），这是最直接的阈值测量
- **INSCYD 之类的代谢组学测试**——测 VO2max、VLamax 等指标，比单一 FTP 信息量大得多
- **功率-时长曲线拟合 / 临界功率（CP 与 W'）模型**——直接从比赛和训练数据里建模，
  不需要专门"测一次"

单一 FTP 测试更多是业余和室内软件的做法。这个定位也说清楚：**本功能是一个可复现的
室内估算工具，不是生理测量。** 它的价值在于"同样的流程、同样的条件下，数字可比"——
用来追踪自己几周几个月的变化是靠谱的，用来和别人的实验室数据比就没意义了。

### 结果会存进训练报告

FTP 测试也会自动存成一份训练报告，里面带着完整的计算过程（依据的功率、折算系数、
有效性和说明）。所以过几个月回头能看出自己的变化轨迹。

## 间歇训练（HIIT / 乳酸阈值）

除了恒定功率，程序内置了 6 个间歇训练方案。在设置区切换到「间歇训练 HIIT」标签，
填 FTP、选方案、按需改参数，下方会实时生成课表预览（柱状图 + 逐段清单），
确认没问题再开始。

### 为什么所有强度都按 %FTP 算

乳酸阈值（LT2，工程上常用 FTP 近似）是**因人而异、也随时在变**的。同样是
"4 分钟高强度"，对 FTP 200W 的人是 190W，对 FTP 300W 的人是 285W。所以方案
只有表达成阈值百分比才谈得上科学——写死瓦数就只是抄了个数字。

区间划分用自行车训练通行的 Coggan 六区：

| 区间 | %FTP | 作用 |
|---|---|---|
| Z1 主动恢复 | < 55% | 促进恢复，几乎不产生训练刺激 |
| Z2 耐力 | 56–75% | 基础有氧，提升脂肪供能与毛细血管密度 |
| Z3 节奏 | 76–90% | 有氧力量，乳酸开始稳定升高但仍可平衡 |
| Z4 乳酸阈值 | 91–105% | 乳酸产生与清除的平衡点附近，直接抬升阈值 |
| Z5 最大摄氧 | 106–120% | 逼近 VO2max，刺激心肺上限 |
| Z6 无氧能力 | > 120% | 短时高强度，主要消耗无氧糖酵解 |

**FTP 怎么估**：最省事的办法是全力骑 20 分钟，取平均功率 × 0.95。或者先用
200W 试一次，体感太轻/太重再调——反正改一个数字整个课表就跟着变。

### 内置方案

| 方案 | 结构 | 主要练什么 |
|---|---|---|
| **30/15 间歇** | 13 × (30s 高强度 / 15s 恢复) | 恢复短于完全清除乳酸所需，乳酸持续累积，提升 VO2max |
| **4×4 分钟** | 4 × (4min / 3min) | Helgerud 经典方案，单段够长能把摄氧量真正顶住 |
| **2×20 阈值** | 2 × (20min @ 98% / 5min) | 训练"清除速率追上产生速率"的平衡点本身，最直接提升 FTP |
| **5×5 分钟** | 5 × (5min / 2.5min) | 比 4×4 更长的累积，对耐受与清除能力要求更高 |
| **Over-Under 超阈值** | 3 大组 × (2min @ 95% + 1min @ 108%) | 在阈值上下反复穿越，乳酸穿梭最直接的练法 |
| **Tabata 20/10** | 8 × (20s 全力 / 10s) | 最狠的一条，原始研究要求每组接近全力 |

### 背后的机制：乳酸穿梭

乳酸不是废物，而是可以被慢肌纤维和心肌重新氧化利用的**燃料**，这个过程叫
乳酸穿梭（lactate shuttle）。反复把乳酸推高、再给一段不完全恢复的时间让它被
清除，这个"推高—清除"的循环本身就是在训练清除能力。

不同方案的差别，本质上就是在"推多高"和"留多久清除"这两个维度上取不同的点：
30/15 和 4×4 偏向持续高位累积，2×20 偏向稳定在平衡点，Over-Under 则是刻意
反复穿越阈值线。

### 训练中的操作

- 圆环显示的是**本段剩余时间**，不是总剩余——HIIT 里你真正关心的是这组还要撑多久，
  总进度在下面用一行小字给出。圆环颜色跟着段类型变（高强度偏暖、恢复偏冷）。
- 下方课表柱状图会实时显示进度：已完成变暗、当前段高亮并带一条进度线。
- 可以「跳过本段」/「上一段」。跳过的时间**不计入训练时长和平均功率**，会单独
  记为"跳过"。
- 训练中可以随时 ±5/±10W，只改**当前这一段**，不会动整个计划。

### 分段统计里的两个细节

**一、达标率只对高强度段计算。** 恢复段的目标是"降下来"，而飞轮有惯性——几秒的
恢复期内功率物理上就降不到目标值。拿"有没有踩到 125W"去评判恢复段只会得到一片
0%，既不公平，也会把整体达标率整个拖垮（实测一条 30/15 课里，混着算出来是 13%，
只看高强度段才有参考价值）。所以恢复/热身/冷身的达标率一列**留空**。

间歇训练的总结页首显示的是「**高强度段达标率**」，恒定功率模式才显示「控功率
达标率」。

**二、每段开头会跳过一小段过渡期。** 最多 5 秒，且不超过该段时长的 1/4。同样是
飞轮惯性的原因：目标功率从 262W 切到 125W 时实际功率需要几秒才能降下来。实测
一个 5 秒恢复段，把过渡期算进去实测均值 125W、达标率 75%；排除后是 100W、100%。
如果某一段实在太短、过渡期之后一点数据都没有，那一行会**留空而不是编一个数字**。

## 自定义课程

如果内置方案都不合口味，切到「自定义课程」标签，点「新建课程」自己排。

每个小节可以有：**类型**（热身 / 高强度 / 恢复 / 冷身）、**名称**、**时长**
（秒或分钟）、**功率**。小节可以上下移动、删除、随时增删，总共最多 80 节。
编辑时下方的课表预览实时更新，确认没问题点「保存课程」，它就变成一个固定课程，
出现在上面的课程列表里，之后随时选中就能开始——和内置 HIIT 方案一样。

> 点「开始训练」会**先自动保存**再开始，所以不用担心辛苦排的课表忘了点保存。

### 功率的两种表示方式

这是自定义课程里唯一需要想一下的地方，所以做成按课程选：

| 方式 | 行为 | 适合 |
|---|---|---|
| **按 %FTP** | 强度跟着你的阈值走，改 FTP 整门课等比缩放 | "我想练阈值"——阈值变了课表该跟着变 |
| **按绝对瓦数** | 每个小节的瓦数固定不变，换 FTP 也不影响 | "我就想稳稳踩 150W"——不关心阈值是多少 |

两种值在保存时都会记下来（而不是只存一份、用的时候换算），所以随时切换表示方式
都不会丢信息：从 %FTP 切到绝对瓦数，之前那份瓦数还在；再切回来，百分比也还在。

内置 HIIT 方案固定用 %FTP，是因为那套方案的立足点就是"乳酸阈值因人而异"。
但自定义课程追求的是自由，所以这里把选择权交给你。

### 小节类型不只是标签

「类型」会影响到训练总结：**只有标成「高强度」的小节才统计达标率**。原因是恢复段
的目标是"降下来"，而飞轮有惯性，几秒的恢复期内功率物理上降不到目标值，拿它算
达标率只会得到一片 0%。所以自己排课时，把真正想考核的小节标成「高强度」，
热身/恢复/冷身按实际标，总结里看到的数字才有意义。

### 保存位置

自定义课程存在 `data/custom_workouts.json`，纯文本，可以直接备份或手改。写入走的
是"临时文件 + 原子替换"，中途断电不会把已有课程写坏；万一文件被改坏了，程序会
安全地忽略它并从空列表开始，不会起不来。

## 关于摩刻 iBike 骑行台

公开渠道查不到摩刻的私有协议文档，但开源项目
[QZ (qdomyos-zwift)](https://github.com/cagnulein/qdomyos-zwift) 里没有摩刻的专用驱动，
说明它是走**标准 FTMS** 的，这也是本程序默认的实现路径。

不过摩刻的家用产品线里有不少是**动感单车**（如 S10 Ultra），这类设备的固件
有可能只实现了「设定阻力」而没有实现「设定目标功率」，或者把 `Set Target Power`
实现成开环查表。在 `auto` 模式下遇到这种情况，程序会先做一次阶跃探测取证，
确认固件确实压不到设定值之后才接管——你不用做任何事。如果你在设置里明确选了
「原生 ERG」，程序就不会自作主张切换，只会提示。

真机上遇到功率长期压不到设定值时，先用 `./run.sh --diag` 把「骑行台回报的阻力
档位」打出来看一眼再下结论——见下方「诊断：为什么功率压不到设定值」。

**验证边界说清楚**：程序有一套完整的模拟设备（骑行台 + 心率带）和 13 套自动化测试，
不需要硬件就能跑通全流程；同时它已经在一台**真实骑行台（FitShow FS-BLE-V3X）**上
连续骑过 60 分钟，报告和曲线都是实测数据。**心率带那条链路目前只用模拟器验证过**
（作者的带子还在路上），所以第一次连真带子时如果扫不到或连不上，把界面上的提示发出来
基本就能定位——错误信息是照着"能直接看出原因"写的。

第一次连一台新设备时，建议先跑一下诊断脚本，把实际的服务结构打出来：

```bash
./run.sh --scan                    # 扫描，确认能搜到骑行台
.venv/bin/python scan.py --pick    # 连接并 dump 完整的 GATT 结构
```

`scan.py` 会直接告诉你这台设备支不支持标准 FTMS、以及能不能接受目标功率。
如果输出里显示「没有发现标准 FTMS 服务」，把完整输出贴出来，就可以针对私有协议
补一个适配层。

## 常见问题

**扫描不到骑行台**
- 确认骑行台已通电，并且被踩动唤醒（很多骑行台静止几分钟就休眠了）
- 关掉手机上正在占用它的 App（Zwift / MyWhoosh / 厂商 App 会独占 BLE 连接）
- 蓝牙只能被一台设备连接。如果骑行台已经被手机连着，电脑就连不上，反之亦然
- 首次运行必须在「系统设置 → 隐私与安全性 → 蓝牙」里给终端授权
- 用 `./run.sh --scan` 看看到底有没有扫到设备

**设备连上了，但「开始训练」按钮是灰的**

先看**页面顶部的消息条**和**按钮下面那行灰字**，它们会直接说明原因。最常见的两种：

1. **这台设备不是标准 FTMS 设备**，或者虽然支持 FTMS 但没提供功率数据。
   程序会在连接阶段就拦下来（而不是让你开个训练却毫无反应），并且把设备
   **实际暴露的服务 UUID 一起列在错误信息里**。把那段信息发出来，就能判断
   要不要为它补一个私有协议适配。也可以直接跑：

   ```bash
   .venv/bin/python scan.py --pick
   ```

2. **骑行台连上后立刻断开了**（休眠、被手机抢走连接、距离太远）。
   消息条会提示「与骑行台的连接断开了」，靠近一点重新连即可。

如果消息条什么都没说、状态灯也是绿的，那说明是浏览器没收到实时状态——程序
每 3 秒会兜底轮询一次，刷新页面即可恢复，按钮也会跟着亮起来。

**骑到一半数据断了**
- 界面会提示「已经有一阵子没收到骑行台数据了」。程序会**停止累计做功和距离、
  也停止调整阻力**，直到数据恢复——不会拿最后一刻的功率值继续算下去。
- 常见原因是骑行台休眠、蓝牙被手机抢走、或者距离太远。靠近一点通常会自动恢复。

**连上了但功率控不住**
- 看界面底部那行提示。如果显示「骑行台没有响应目标功率（目标从 … 阶跃到 … 后功率
  仍停在 …），已自动切换到闭环阻力控制」，说明探测取证之后降级已经发生，稍等
  一会儿功率就会收敛。如果是「探测通过：骑行台确实在跟目标功率」，那说明固件只是
  整定有偏差，程序会留在原生 ERG，不走闭环
- 闭环模式下必须保持踩踏。踏频低于 25rpm 时不调整阻力（这是有意设计的）
- 如果两种方式都不行，跑 `scan.py`，多半是固件走的是私有协议

**训练到一半不小心关了服务 / 点了断开**
- 这一场会**照常存成报告**（结束原因写「断开连接」），在训练报告里能看到，不想要直接删掉。
  以前这种情况会静默丢掉整场训练。

**手机关掉页面、电脑接着骑**
- 训练跑在电脑端，刷新或关掉页面不影响；重新打开页面会自动接上当前状态。

**手机打不开页面**
- 手机和电脑要在同一个 Wi-Fi 下（注意别一个连 5G 一个连访客网络）
- macOS 防火墙可能拦了 8765 端口，在「系统设置 → 网络 → 防火墙」里放行
- 用启动时终端打印的那个 `192.168.x.x` 地址，不要用 `127.0.0.1`

**想换数据存放位置 / 备份训练记录**
- 数据默认放在项目下的 `data/`。设一个环境变量就能换到别处：

  ```bash
  IBIKE_DATA_DIR=~/Documents/ibike-data ./run.sh
  ```

- 报告是纯文本，直接拷走 `data/reports/` 就是备份。想清空记录可以在界面上操作，
  也可以直接删文件。

## 已验证内容

下面 13 套测试全部基于模拟骑行台/模拟 BLE 外设，**不需要任何硬件**：

```bash
.venv/bin/python selftest.py                     # 端到端：协议 + 控制 + 接口
.venv/bin/python tests/test_trainer_mock.py      # 真机代码路径（模拟 GATT 外设）
.venv/bin/python tests/test_connect_flow.py      # 连接流程健壮性
.venv/bin/python tests/test_summary.py           # 训练总结
.venv/bin/python tests/test_intervals.py         # 间歇训练
.venv/bin/python tests/test_custom_courses.py    # 自定义课程
.venv/bin/python tests/test_session_lifecycle.py # 会话状态机与并发
.venv/bin/python tests/test_reports.py           # 训练报告
.venv/bin/python tests/test_ftptest.py           # FTP 测试
node tests/test_frontend_smoke.js                # 前端冒烟（需要 node）
.venv/bin/python tests/test_diag.py              # 原生 ERG 诊断脚本的判读规则
.venv/bin/python tests/test_server_hardening.py  # 服务端加固（实时推送/断开存报告/跨站/畸形输入）
.venv/bin/python tests/test_heartrate.py         # 心率带：帧解析、区间、上限保护、接口
```

> 测试会把自己的数据写到临时目录（靠 `IBIKE_DATA_DIR`），**不会碰你的真实训练记录**。
> 这一条有测试专门守着——训练报告是"训练一结束就自动保存"的，不隔离的话跑一次
> 测试就会往 `data/reports/` 里留下一条记录。

`selftest.py` 覆盖：FTMS 编解码（`Indoor Bike Data` 位域解析含跳位与截断容错、
能力声明、`Set Target Power` / `Set Target Resistance` 指令编码、控制点应答含
`Control Not Permitted`）、**原生 ERG 路径**（稳定在 100W，实测 99~101W）、
**闭环阻力路径**（在线辨识系数 k，收敛到 100W ±6W，稳态 95~104W）、
**自动降级**（模拟「声明支持目标功率但不执行」的骑行台，验证先阶跃探测取证、
确认它压不到设定值之后才切换）、**探测通过不降级**（模拟一台「前半段没睡醒、
一被探测就正常闭环」的骑行台，验证不会被误降级）、以及 HTTP / WebSocket 接口全流程。

`tests/test_trainer_mock.py` 用假的 BLE 外设驱动真实的 `TrainerClient`：

- 服务发现、能力探测（厂商/型号/电量/功率范围/阻力范围）、订阅、数据解析
- 控制指令序列：申请控制权 → Start/Resume → 目标功率，编码逐字节校验
- 固件不回应答时不会卡死：等待时间 **2.5 秒 → 连续 3 次超时后放宽到 0.4 秒**，
  避免每 2 秒一次的保活把训练主循环堵死；而"响应慢但确实会应答"的固件不会被
  误判（放宽只对从未应答过的固件生效）
- 被拒绝控制权（`Control Not Permitted`）后自动重申请并重发
- 缺少 Feature 特征值时保守处理
- **不是 FTMS 设备时给出可诊断的错误**，错误信息里带上设备实际暴露的服务 UUID
- 有控制点但没有功率数据时提前拦截（否则会变成"开了训练却毫无反应"）

`tests/test_connect_flow.py` 盯住连接流程：连接成功后快照里必须带
`trainer.connected`（前端靠它点亮按钮）；连接失败后必须清干净状态，不能留下
"看似连上、其实不能用"的半成品；失败后重试要能成功。

`tests/test_summary.py` 覆盖训练总结：曲线降采样必须保住孤立尖峰、功率区间
分档正确且合计 100%、NP 算法（恒定功率下等于平均值，波动越大越高）与 60 秒
有效性门槛、完整训练与提前结束两条路径、关闭总结后能马上开始新训练。

`tests/test_intervals.py` 覆盖间歇训练：六区划分、6 个方案都能生成合法的
「热身→重复组→冷身」结构、强度按 FTP 严格线性缩放、越界参数被夹回范围、
步骤定位的边界（时刻正好落在段边界时算下一段）、会话按时间自动推进且只进不退、
跳过/回退的越界保护、分段统计跳过过渡期、HTTP 的模板/预览/启动/跳过/重复全流程。

`tests/test_custom_courses.py` 覆盖自定义课程：保存/重新加载/更新/删除的持久化、
两种功率表示模式（绝对瓦数不随 FTP 变、百分比跟着缩放）、切换模式不丢信息、
越界与非法输入的处理、**损坏的存储文件不会让程序起不来**、HTTP 的
新建/保存/列出/草稿预览/已存预览/删除、用自定义课程真正跑一次训练（分段总结、
高强度节才有达标率、再来一次能复现同一门课）、单节课程等价于恒定功率。

`tests/test_session_lifecycle.py` 专门盯状态机与并发：暂停中重开不会留下孤儿主循环、
反复开始/停止/关闭不会堆积任务、重复停止是幂等的、运行中重开被明确拒绝、计时速率
为 1.0×、跑满时长后循环自行退出；以及三条来自实测的故障场景——

- **设备停止上报数据**（链路还在）时，必须识别为数据陈旧、停止积分、停止调阻力，
  并在数据恢复后自动继续；不能拿最后一帧的功率一直算下去。
- **一路跳过到终点**不能被标成「训练完成」。
- **开始训练时下发失败**（固件回 Operation Failed）后，状态必须是 error 且骑行台
  已释放，不能留下"状态是 idle 但设备被占住"。

`tests/test_reports.py` 覆盖训练报告：保存/列表/读取/删除/清空、按时间倒序、
坏文件与无关文件不影响列表、超过上限时丢掉最旧的、**id 的路径穿越防护**（9 种
恶意 id 都被拒绝且目录外的诱饵文件没被动过）、HTTP 全流程、训练自然结束后自动
保存（且同一次训练不会重复保存）、"重启"后报告还在、示例报告的标记与单独清理、
以及**数据目录隔离机制本身是生效的**。

`tests/test_ftptest.py` 覆盖 FTP 测试：三个方案都能生成合法课表、坡道逐级递增、
**20 分钟测试里那次 5 分钟全力排在计时段之前**、计时段才是被测量的段、控制方式由
方案决定（坡道 ERG、其余自由骑行）、参数越界夹取；会话层面验证了坡道跑完能算出 FTP、
**踩不动了会自动判力竭并结束**、**自由骑行全程不下发任何目标功率**（这是测试有效的前提）、
自由骑行可以微调阻力、计时段测试取较好的一次、**跑完全部级数却没力竭会标记为无效**、
力竭结束不算"提前结束"。

`tests/test_frontend_smoke.js` 用一层 DOM 桩在 Node 里**真的加载并执行** `app.js`，
然后喂给它 7 组「服务端可能推过来的状态」（未连接、恒定功率运行中、间歇运行中、
暂停、出错、恒定总结、间歇总结含数据不足的分段）调用 `render()`，再验证报告列表 /
打开报告 / 返回列表的面板切换、画布尺寸、以及 16 个关键回调都已绑定。`node --check`
只能查语法，这个测试能查运行时——空引用、字段拼错、函数没定义都跑不掉。

它自己也验证过**有效性**：故意注入的四类 bug 都被抓了出来——「渲染时引用不存在的
元素」「总结里访问不存在的字段」「加载期绑定不存在的元素」「把画布尺寸钉死的那行
去掉」（最后一个会精确复现"每画一次图就大一圈"：`1200x360 → 2400x720 → 4800x1440
→ …`）。

此外还通过真实入口 `main.py --sim` 端到端跑过恒定功率、间歇训练、自定义课程各一次，
并验证了报告在训练结束后自动落盘、列表/查看/删除/路径穿越拦截都正常。

**尚未验证的部分**：真实摩刻 iBike 骑行台上的蓝牙通信。协议层（FTMS）和
控制逻辑已经完整验证，但真机的服务结构、固件是否响应目标功率、阻力档位量程
这些只能接上真机才能确认——`scan.py` 就是为此准备的。

如果接上真机后发现闭环控制收敛得不够好（每台车的阻力-功率特性都不一样），
可以用调参工具看轨迹：

```bash
.venv/bin/python tools/tune_closed_loop.py --seconds 90 --tail 30
```

## 说明与已知限制

- 服务默认监听 `0.0.0.0:8765`，局域网内任何设备都能访问，**没有任何鉴权**。
  只在可信网络里使用，别把这个端口暴露到公网。
- **训练报告会持久保存**（`data/` 下），但**实时训练中的曲线只存在内存里**——
  训练中途刷新页面会丢掉已经画出来的那半截曲线，历史报告不受影响。
- 报告里的心率只有**心率本身的统计**（平均/最大/区间分布/曲线）。没有做
  **静息 HRV**（要用到 RR 间期，需要训练前单独静坐采集），也没有训练负荷指标
  之间的心率交叉分析（解耦率、心率漂移、EF 趋势）——这些是下一批候选功能，
  清单见 `docs/heart-rate-features.md`。
- 报告里**没有 TSS / IF 这类训练负荷指标**，因为算它们需要一个另外测出来的 FTP 值，
  而程序不假装知道你真实的阈值——想要的话可以自己按 NP 和 FTP 口算。
- **没有训练计划日历**，不能排"下周三做 4×4"。报告只是记录，不是计划工具。
- 界面**没有鉴权也没有多用户**，同一时刻只维护一个训练会话（两个标签页同时操作
  会互相干扰，服务端有并发保护，但体验上不推荐）。
- **只支持蓝牙 FTMS**。不支持 ANT+，也没有为任何厂商私有协议做适配——如果你的
  骑行台不说标准 FTMS，用 `scan.py` 打出它的服务结构发过来，才有可能加上。
- **没有导出功能**。报告是纯文本 JSON，想要 GPX/CSV 之类的格式需要自己转。

下面几条是 2026-09 那次全面代码审查里确认过、但**评估后决定先不修**的问题，
写在这里是为了留个底，不是待办清单：

- **报告列表会同步解析全部报告文件**。500 份（约 15MB）时 `GET /api/reports`
  要 0.16 秒，这段时间里 ERG 控制循环也被卡住。报告数量还少的时候没有实际影响；
  真要治就得给每份报告加一个轻量索引文件。
- **自定速（目标功率 0）的 FTP 测试里，"功率分布"只覆盖热身段**，因为分档是按
  目标功率的百分比划的，而自由骑行段没有目标。百分比仍然合计 100%，但分母不是
  整场时长。
- **坡道测试如果在最后一级力竭**，报告会说"跑完了全部 N 级还没力竭"（结论是
  "坡道太短"），和实际不符。多留几级余量就不会碰到。
- **坡道测试的最高一级可以到 2200W**，而恒定功率模式的上限是 2000W。
- **`scan.py --pick` 的序号没有越界检查**，输入一个不存在的编号会抛异常退出。
