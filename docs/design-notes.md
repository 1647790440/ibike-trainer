## 控功率的两条路径

程序会优先尝试**原生 ERG**，不行就自动退到**闭环阻力**。这是为了兼容那些
FTMS 实现不完整的固件。

| 方式 | 原理 | 特点 |
|---|---|---|
| **原生 ERG** | 下发 `Set Target Power (0x05)`，骑行台固件自己闭环调阻力 | 响应快、手感好，和 Zwift 一样。需要固件真正支持 |
| **闭环阻力** | 只下发 `Set Target Resistance Level (0x04)`，本程序读回实际功率，用自适应控制器不断修正档位 | 兼容性最好。响应稍慢，但能把功率控住 |
| **自由骑行** | 设一次阻力就撒手，功率完全靠骑手配速 | FTP 测试的 20/8 分钟计时段必须用这个 |

闭环控制器建立在「功率 ≈ 系数 × 阻力档位 × 踏频」这个近似上，并在骑行过程中
**在线辨识**那个系数：

```
k ← (1-α)·k + α·(P / (R·C))
ΔR = β · (P目标 - P实测) / (k · C)
```

用辨识出的 `k` 归一化意味着**踏频变化会被自动补偿**——踏频掉了，阻力会自动补上，
这正是 ERG 该有的手感。踏频低于 25rpm 时控制器会暂停调整，免得你重新踩起来时
阻力大得踩不动。

两个抗振荡的细节（少了它们功率会来回冲）：β 取 0.55 而不是 1，每步只修正一部分
误差；而且只在阻力稳定下来之后才去辨识 `k`，不拿过渡过程的数据去污染模型。
实测调整前后：

| | 稳态功率区间 | 峰峰值 |
|---|---|---|
| 一次修正到位（β=1，2 秒一调） | 78 ~ 119 W | 41 W |
| **现在的参数**（β=0.55，4 秒一调） | **95 ~ 104 W** | **9 W** |

闭环控制的起始档位取的是**骑行台当前实际所在的档位**，而不是量程的中间值。
这一点很重要：无论从原生 ERG 切过来、还是暂停之后继续，阻力都从原地接手。
早期版本固定从"量程的四分之一"起步，于是每次切入都会先掉一大截再慢慢爬回来——
实测过一次 1 小时 130W 的训练，阻力从 17 掉到 6、花了一分多钟才爬回 17。

## 自动降级：先立案，再取证

如果骑行台声明支持目标功率、但实际压根不理会（收下指令回 Success，功率却纹丝
不动），程序会识别出来并**自动切换到闭环阻力控制**：

```
1. 立案：连续 18 秒功率都在 ±max(8W, 目标 6%) 容差带之外，且标准差 < 8W
2. 取证：临时把目标功率往下压 25W，观察 20 秒
   ├─ 功率跟着往下走 ≥ 8W  → 固件确实在响应，保留原生 ERG，10 分钟内不再打扰它
   └─ 功率纹丝不动         → 实证固件不响应，才切换到闭环阻力
```

**为什么第二步不能省**：功率稳、却稳定偏离目标，光凭这一条是分不清"固件装死"和
"固件在跟、只是整定有偏差"的。动感单车的功率常常是固件用「阻力 × 踏频」算出来的，
骑手踏频一稳，功率就能稳得毫无波动，看起来像固件不理人，其实它正在慢慢把阻力加
回去。真机上就踩过这个坑：一次 60 分钟 130W 的骑行，功率平稳地掉到 114W 并保持了
一分多钟，程序据此判成"固件装死"就把控制权切走了——而用户明明选的是 `auto`
（本意就是"用原生 ERG"）。切换的代价很大（控制权整个易手，骑手能立刻感到阻力
跳变），所以现在宁可先花 20 秒取证。

两条相关规则：

- **明确选了「原生 ERG」就绝不自动切换。** 自动降级只是 `auto` 模式为了兼容性
  兜的底，不该反过来覆盖用户的明确选择。
- **FTP 测试期间不做这个降级判断。** 坡道测试每级都在抬高目标，功率本来就滞后
  几秒，正好落进"稳但偏"的判据里；一旦降级成闭环阻力，阻力被锁死，坡道就再也
  加不上去。同理，普通课表换段之后也会把观察窗口清零。

## 诊断脚本：为什么功率压不到设定值

```bash
./run.sh --diag              # 约 4 分钟，全程保持踩踏
./run.sh --diag --sim        # 没有硬件时先看一眼输出长什么样
./run.sh --diag --quick      # 每个阶段 30 秒
```

它比训练报告多给出一列关键数据：**骑行台自己回报的阻力档位**。原生 ERG 模式下
程序一个阻力指令都没发过，所以这一列完全是固件的行为，也正是回答"它到底有没有在
调阻力"的唯一直接证据。诊断跑三个对照阶段：

| 阶段 | 做什么 | 用来排除什么 |
|---|---|---|
| **A** | 原生 ERG + 每 2 秒重发目标功率（程序现在的做法） | 基准 |
| **B** | 原生 ERG + 只在开头发一次 | 每 2 秒重发会不会打断固件自己的积分器 |
| **C** | 目标功率 +40W / −40W 阶跃 | 固件对"设定值"到底有没有伺服能力 |

跑完直接给结论，四种可能：阻力一动不动（开环查表，用闭环阻力）、阻力在动但功率
停不下来（刻度偏差或死区太大，用闭环阻力）、阶段 B 明显比 A 好（重发打断了积分器，
放宽 `POWER_KEEPALIVE_S`）、功率稳在目标附近（原生 ERG 没问题）。

**一个实测发现：回报的阻力档位和设置的阻力档位不是一个量纲。** 真机上
（FitShow FS-BLE-V3X）原生 ERG 模式下它回报的 `Resistance Level` 换算成显示值是
**1.7~3.2**，而程序用闭环控制时要设到 **15~20** 才能维持同样的功率——也就是说
固件上报的是它自己的档位刻度，不是你下发下去的那个值。所以看诊断结论时只能看
**"它动没动"**，不要拿绝对值和下发的值对比。想知道它自己声明的量程，跑
`./run.sh --diag`，开头会打印 `阻力量程(原始值)`。

**这个脚本是怎么来的**：一次真实的 60 分钟 130W 骑行里，功率在 t≈912~930 秒整整
一段**每一个采样点都精确等于 114W**——而目标是 130W。人的腿不可能这么稳，所以那
几秒里骑行台报的功率必然是它自己用「阻力 × 踏频」算出来的固定值：**阻力没动，
功率就没动**。

再看全程，这种"12 秒完全不动"的平台在原生 ERG 段占 22%，平台值散布在 76 / 114 /
116 / 118 / 119 / 124 / 126 / 129 / 131 / 134 / 163 W——一个真正在闭环的 ERG 不可能
让功率稳定地停在偏离目标 30W 的地方。也就是说：它报的"支持目标功率"是个声明，
不是保证。区别只在于"它为什么不动"，一小时的功率曲线分不出来——缺的就是**回报的
阻力档位**那一列。

## 数据存储

### 训练报告

一次训练一个文件，纯文本 JSON，在 `data/reports/` 下。之所以不是把所有报告塞进
一个大文件：报告只增不减，单文件方案每存一次都要重写全部历史，数据量一大就慢，
而且写坏一次全部丢失。

- **上限 500 份**（每份含曲线约 30KB，合计约 15MB）。超出后删除最旧的，并在日志里
  明确记一条——不静默丢用户数据。
- **写入走"临时文件 + `os.replace`"**，中途断电不会留下半截文件。
- **报告 id 来自客户端，所以做了白名单校验**：只允许字母数字和 `-`/`_`，解析完
  还要确认结果仍在报告目录内——两道保险挡住 `../` 这类目录穿越。
- **列表接口不返回功率曲线**。列表只需要几个数字，没必要把几十 KB 的轨迹传一遍。
- 目录里混进坏文件或不相关文件时会被跳过并记日志，不会让整个列表打不开。
- 报告里保留**功率、目标、阻力、踏频、心率**五列轨迹。阻力和踏频是有意留着的——
  报告是事后复盘问题的唯一依据，把这两列丢掉的话，"阻力为什么突然变了"这类问题
  就完全无从查起（真的遇到过）。
- 报告里还记录**控功率方式的切换**（什么时候、从什么切到什么、为什么）。

### 自定义课程与设置

`data/custom_workouts.json` 和 `data/settings.json`，同样是纯文本 + 原子写入。
被改坏时程序会安全地忽略、退回默认值或空列表并留下备份，不会起不来；
读不出来的课程条目会被原样保留，不会在下次保存时被抹掉。

## 项目结构

```
├── main.py              入口（--scan / --sim / --sim-dumb / --diag）
├── run.sh               启动脚本：自动建虚拟环境、装依赖、起服务
├── scan.py              诊断脚本：dump 蓝牙设备的服务/特征值结构
├── selftest.py          自检：协议 + 两条控制路径 + 自动降级 + HTTP 接口
├── tests/               12 套测试（见下）
├── tools/
│   ├── make_sample_reports.py  生成示例训练报告
│   └── tune_closed_loop.py     闭环控制器调参：打印功率轨迹和波动幅度
├── docs/                说明文档（本目录）
└── ibike/
    ├── ftms.py          FTMS 协议层：UUID、数据解析、指令编码（纯函数，可单测）
    ├── ble.py           蓝牙广播扫描：一次扫描，骑行台和心率带共用这份结果
    ├── trainer.py       真实骑行台的 BLE 客户端（扫描/连接/订阅/指令/重连）
    ├── heartrate.py     心率带：标准心率服务客户端、帧解析、区间、模拟心率带
    ├── simulator.py     模拟设备（骑行台 + 心率带），无硬件也能跑通全流程
    ├── workouts.py      内置间歇方案与区间划分（全部按 %FTP 定义）
    ├── custom.py        自定义课程：存储、校验、展开成训练计划
    ├── ftptest.py       FTP 测试方案：坡道 / 20 分钟 / 8 分钟
    ├── diag.py          原生 ERG 诊断：把「回报的阻力档位」打出来并给结论
    ├── settings.py      本地设置：FTP、心率参数、记住的心率带地址
    ├── reports.py       训练报告：本地保存、列表、读取、删除
    ├── paths.py         数据目录位置（测试靠它隔离到临时目录）
    ├── session.py       训练会话：计划推进、倒计时、统计、两条控制路径、心率上限保护
    ├── server.py        aiohttp 后端：REST + WebSocket + 二维码
    └── web/             前端界面（原生 JS，零依赖，手机适配）
```

`simulator.py` 和 `trainer.py` 是两条完全不同的代码路径——前者从不出错，
所以**光靠模拟器测不到真机上的问题**。`tests/test_trainer_mock.py` 用一个假的
BLE 外设把真实的 `TrainerClient` 跑起来，覆盖服务发现、能力探测、订阅、指令应答
匹配、以及各种"固件有毛病"的情况。

```bash
.venv/bin/python tests/test_reports.py           # 训练报告
.venv/bin/python tests/test_ftptest.py           # FTP 测试
.venv/bin/python tests/test_heartrate.py         # 心率带：帧解析、区间、上限保护、接口

node tests/test_frontend_smoke.js                # 前端冒烟（需要 node）
```

测试会把自己的数据写到临时目录（靠 `IBIKE_DATA_DIR`），**不会碰你的真实训练记录**。
这一条有测试专门守着。

覆盖到的关键行为（都是踩过坑之后补上的回归）：

- FTMS 编解码：`Indoor Bike Data` 位域解析（含跳位、截断、More Data 语义）、
  能力声明、指令编码逐字节校验、控制点应答（含 `Control Not Permitted`）
- 控功率两条路径的收敛性、自动降级（含"先探测取证"）、明确选了原生 ERG 时不降级
- 数据陈旧（链路还在但设备不再上报）时必须停止积分、停止调阻力，不能拿冻结值算下去
- 暂停/断链的时间不能被算进"这一小节骑了多久"（会影响分段统计和 FTP 有效性）
- 断开骑行台不影响心率带的读数；反过来也一样
- 训练中断开连接 / 关服务时，这一场要照常落盘成报告
- 报告 id 的目录穿越、损坏文件不影响启动、上限裁剪
- 服务端：跨站请求拦截、畸形 JSON 不 500、请求体过大如实回 413
- 前端：状态渲染、两页切换、设备块、报告里的心率与切换记录

## 关于设备兼容性（摩刻 / 动感单车）

公开渠道查不到摩刻（MOKFitness）的私有协议文档，但开源项目
[QZ (qdomyos-zwift)](https://github.com/cagnulein/qdomyos-zwift) 里没有摩刻的专用驱动，
说明它走的是**标准 FTMS**——这也是本程序默认的实现路径，理论上任何标准 FTMS
设备都能用。

需要留意的是：不少家用产品线是**动感单车**（如摩刻 S10 Ultra），这类设备的固件
有可能只实现了「设定阻力」而没有实现「设定目标功率」，或者把 `Set Target Power`
实现成开环查表。在 `auto` 模式下遇到这种情况，程序会先做一次阶跃探测取证，确认
固件确实压不到设定值之后才接管——用户不用做任何事；如果明确选了「原生 ERG」，
程序不会自作主张切换，只会提示。

遇到功率长期压不到设定值时，先跑 `./run.sh --diag` 把「骑行台回报的阻力档位」
打出来看一眼再下结论。

## 说明与已知限制

- 服务默认监听 `0.0.0.0:8765`，局域网内任何设备都能访问，**没有任何鉴权**。
  只在不担心的网络里用，别把这个端口暴露到公网。
- **只支持蓝牙 FTMS**。不支持 ANT+，也没有为任何厂商私有协议做适配。
- **实时训练中的曲线只存在内存里**——训练中途刷新页面会丢掉已经画出来的那半截
  曲线，历史报告不受影响。
- 报告里**没有 TSS / IF 这类训练负荷指标**，因为算它们需要一个另外测出来的 FTP 值，
  而程序不假装知道你真实的阈值。
- **没有训练计划日历**，不能排"下周三做 4×4"。报告只是记录，不是计划工具。
- **没有导出功能**。报告是纯文本 JSON，想要 GPX/CSV 之类的格式需要自己转。
- 界面**没有多用户**，同一时刻只维护一个训练会话（两个标签页同时操作会互相干扰，
  服务端有并发保护，但体验上不推荐）。
- **验证边界**：程序已经在一台真实骑行台（FitShow FS-BLE-V3X）上连续骑过 60 分钟，
  但**心率带那条链路只用模拟器验证过**。第一次连真带子时如果扫不到或连不上，
  把界面提示发到 issue 里基本就能定位。

### 已知但暂时不修的问题

评估过、影响很小、暂时留着的问题，写在这里留个底：

- **报告列表会同步解析全部报告文件**。500 份（约 15MB）时 `GET /api/reports` 要
  0.16 秒，这段时间里 ERG 控制循环也被卡住。要治就得给每份报告加一个轻量索引文件。
- **自定速（目标功率 0）的 FTP 测试里，"功率分布"只覆盖热身段**，因为分档是按
  目标功率的百分比划的，而自由骑行段没有目标。百分比仍然合计 100%，但分母不是
  整场时长。
- **坡道测试如果在最后一级力竭**，报告会说"跑完了全部 N 级还没力竭"，和实际不符。
  多留几级余量就不会碰到。
- **坡道测试的最高一级可以到 2200W**，而恒定功率模式的上限是 2000W。
- **距离/速度是骑行台自己报的**。动感单车没有真实位移，固件通常按「踏频 × 固定齿比」
  折算（实测 30 分钟显示 12.5km），这个数只适合自己跟自己比，不要当成实际里程。
- **`scan.py --pick` 的序号没有越界检查**，输入一个不存在的编号会抛异常退出。
