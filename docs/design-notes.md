## 控功率的两条路径

程序会优先尝试**原生 ERG**，不行就自动退到**闭环阻力**。这是为了兼容那些
FTMS 实现不完整的固件。

| 方式 | 原理 | 特点 |
|---|---|---|
| **原生 ERG** | 下发 `Set Target Power (0x05)`，骑行台固件自己闭环调阻力 | 响应快、手感好，和 Zwift 一样。需要固件真正支持 |
| **闭环阻力** | 只下发 `Set Target Resistance Level (0x04)`，本程序读回实际功率，用自适应控制器不断修正档位 | 兼容性最好。响应稍慢，但能把功率控住 |
| **自由骑行** | 设一次阻力就撒手，功率完全靠骑手配速 | FTP 测试的 20/8 分钟计时段必须用这个 |

闭环控制器建立在「功率 ≈ 系数 × 阻力档位 × 踏频」这个近似上，并在骑行过程中
**在线辨识**那个系数：

```
k ← (1-α)·k + α·(P / (R·C))
ΔR = β · (P目标 - P实测) / (k · C)
```

用辨识出的 `k` 归一化意味着**踏频变化会被自动补偿**——踏频掉了，阻力会自动补上，
这正是 ERG 该有的手感。踏频低于 25rpm 时控制器会暂停调整，免得你重新踩起来时
阻力大得踩不动。

两个抗振荡的细节（少了它们功率会来回冲）：β 取 0.55 而不是 1，每步只修正一部分
误差；而且只在阻力稳定下来之后才去辨识 `k`，不拿过渡过程的数据去污染模型。
实测调整前后：

| | 稳态功率区间 | 峰峰值 |
|---|---|---|
| 一次修正到位（β=1，2 秒一调） | 78 ~ 119 W | 41 W |
| **现在的参数**（β=0.55，4 秒一调） | **95 ~ 104 W** | **9 W** |

闭环控制的起始档位取的是**骑行台当前实际所在的档位**，而不是量程的中间值。
这一点很重要：无论从原生 ERG 切过来、还是暂停之后继续，阻力都从原地接手。
早期版本固定从"量程的四分之一"起步，于是每次切入都会先掉一大截再慢慢爬回来——
实测过一次 1 小时 130W 的训练，阻力从 17 掉到 6、花了一分多钟才爬回 17。

## 自动降级：先立案，再取证

如果骑行台声明支持目标功率、但实际压根不理会（收下指令回 Success，功率却纹丝
不动），程序会识别出来并**自动切换到闭环阻力控制**：

```
1. 立案：连续 18 秒功率都在 ±max(8W, 目标 6%) 容差带之外，且标准差 < 8W
2. 取证：临时把目标功率往下压 25W，观察 20 秒
   ├─ 功率跟着往下走 ≥ 8W  → 固件确实在响应，保留原生 ERG，10 分钟内不再打扰它
   └─ 功率纹丝不动         → 实证固件不响应，才切换到闭环阻力
```

**为什么第二步不能省**：功率稳、却稳定偏离目标，光凭这一条是分不清"固件装死"和
"固件在跟、只是整定有偏差"的。动感单车的功率常常是固件用「阻力 × 踏频」算出来的，
骑手踏频一稳，功率就能稳得毫无波动，看起来像固件不理人，其实它正在慢慢把阻力加
回去。真机上就踩过这个坑：一次 60 分钟 130W 的骑行，功率平稳地掉到 114W 并保持了
一分多钟，程序据此判成"固件装死"就把控制权切走了——而用户明明选的是 `auto`
（本意就是"用原生 ERG"）。切换的代价很大（控制权整个易手，骑手能立刻感到阻力
跳变），所以现在宁可先花 20 秒取证。

两条相关规则：

- **明确选了「原生 ERG」就绝不自动切换。** 自动降级只是 `auto` 模式为了兼容性
  兜的底，不该反过来覆盖用户的明确选择。
- **FTP 测试期间不做这个降级判断。** 坡道测试每级都在抬高目标，功率本来就滞后
  几秒，正好落进"稳但偏"的判据里；一旦降级成闭环阻力，阻力被锁死，坡道就再也
  加不上去。同理，普通课表换段之后也会把观察窗口清零。

## 自动暂停：停表这件事，要停得干净

真机上踩过的坑：135W 骑到第 42 分钟来了个电话，骑手停下来接电话，没按暂停。
那 2 分钟被算成骑行时长，报告里的平均功率从 135W 摊成 130W、达标率掉了一大截。
所以现在"功率和踏频都归零"超过 15 秒就自动停表，重新踩起来自动继续。

几个刻意做成这样的地方：

- **判据是"与"不是"或"**：功率 ≤5W **且** 踏频 ≤5rpm 才算没在骑。只看功率会
  把自由骑行里"在踩但只有几瓦"误判成停踩；只看踏频又会把"溜车"当成在骑。
- **停止累计是当场生效的，标记暂停要等满 15 秒**。两者分开：确认"不是抖动"
  需要那 15 秒，但记账一秒都不能等——否则每次自动暂停都会在报告里留下十几秒
  0W，平均功率照样被摊薄（这正是要消灭的东西）。15 秒里如果又踩起来了，
  那段空档同样没被算进去。
- **自动暂停是"软"的：不动骑行台**。手动暂停会下发 FTMS Stop/Pause 让台子松开，
  自动暂停不能这么干——固件收到暂停后可能放开阻力、甚至停推 Indoor Bike Data，
  那样就再也收不到踏频，"骑手回来了"永远检测不到，自动继续就成了空话。
- **自动继续看踏频，不看功率**：暂停期间台子上的阻力是放开的，重新踩起来那几秒
  功率可能还不到 20W，光等功率会出现"永远不自动继续"。要求踏频连续达标 3 秒，
  碰一下曲柄不会开表。
- **只有自动暂停才允许自动继续**。手动按下的暂停是"我就是要停着"，骑行台掉线
  挂起是"台子都没了"——这两种情况踩起来都不许自己跑起来，必须用户点「继续」。
- **坡道测试不吃这套**：它有自己的力竭判据（踏频掉到 50 以下持续 3 秒），
  踩不动了要结束成"力竭"；自动暂停要是抢先停表，测试就永远等不到那个结论。

时间轴（阈值）都在类属性上，测试可以压到秒级；`AUTO_PAUSE_ENABLED = False`
就退回"秒表一直走"的老行为。

## 骑行台掉线：挂起、自动重连、骑起来自动继续

除了"挂起不结束"，现在还会**自己把骑行台接回来**。真机实测的完整时间线：

| 时刻 | 发生了什么 |
|---|---|
| 0s | 骑手停下来不踩 |
| 15s | 程序自动暂停（秒表冻结，统计从 0s 起就不再累计） |
| ~47s | 台子自己报 `Stopped` |
| ~109s | 台子自动关机，蓝牙断链 |
| 之后每 5-30s | 程序后台试着重连（台子要等骑手踩醒才广播，所以不设"重试几次就放弃"） |
| 骑手重新踩 | 连上 → **立刻 Start/Resume 让台子重新跑起来** → 数据恢复 → 连续 3 秒踏频或功率达标 → **自动继续这一场训练** |

以前这条路的每一步都要人来点：回设备页、扫描、点设备、回训练页、点继续。一次长休息
走一遍，实测一场 66 分钟的训练里走了三遍。

实现分三层，各自的理由：

- **`session` 判断"台子不见了"**：数据沉默超过 `STALE_SUSPEND_S`（20 秒）就挂起。
  为什么不能只靠断连回调：蓝牙半开、台子静静断电的时候回调可能一直不来，**数据的
  沉默才是唯一可靠的信号**。这条检查放在状态分发之前，所以"还在骑"和"已经自动暂停"
  两种状态都能走到。
- **`server._auto_reconnect_loop()`**：只在训练还没结束时工作，退避到 20 秒一次一直
  重试；接上就走 `rebind_trainer`（训练本体原样保留）。用户主动点「断开」会停掉它，
  不能偷偷连回来。三个坑：
  1. `_connect_trainer` 开头会调 `_disconnect_trainer`，而后者会调
     `_stop_auto_reconnect`——从重连任务自己走进去时，**既不能 cancel 自己**
     （下一个 await 点会抛 CancelledError，把刚建好的连接毁掉），**也不能把
     `auto_reconnecting` 抹成 False**（循环下一轮就以为被取消了，一次失败之后就
     再也不重试，而"台子还没被踩醒"时第一次必然失败）。
  2. **不能只按记住的地址直连**。第一版就是这么写的：只要存过地址就返回它、
     永远不扫描——结果真机上直接翻车，用户看到的是"程序并没有自动扫描、自动连接"。
     原因是**骑行台断电重连之后，macOS 眼里的 UUID 会变**（BLE 随机地址），旧地址
     从此是死的。现在每轮都先扫一遍广播，**把刚扫到的地址排在前面**、旧地址放最后
     兜底；短暂断链（地址还有效）时第一轮直连就能连上，不用等扫描。
  3. 重连过程必须留下事件（`trainer-reconnecting` / `trainer-reconnected`）。
     没有它，报告里"自动重连到底跑没跑、失败在哪一步"完全看不出来——第一版就是
     因为只有一句 `log.info`，出问题时只能猜。
- **`session` 决定"骑起来了"**：挂起同样标记成"不是用户按的"（`auto_paused`），
  所以自动继续对它有效；但条件比自动暂停严格——必须骑行台已经接回来、数据是新鲜的、
  而且**踏频或功率**连续达标 3 秒。手动按下的暂停仍然必须等用户点「继续」。
- **接回来的那一刻就要 Start/Resume**（只 Start，不下发目标功率）。这是第二次真机
  翻车换来的：骑行台重新上电后处在它自己的 `Stopped` 状态，会安安静静地推
  `0W / 0rpm` 的帧——数据是"新鲜"的（所以既不触发掉线判断、也不触发沉默挂起），
  但骑手踩得再久也满足不了达标条件，自动继续就死锁在那儿（实测死了 2 分多钟，
  用户以为"没连上"）。只发 Start 不发目标，是为了不把站在车边转曲柄的人一上来
  就顶到 140W。
- **踏频不是唯一证据**：同一台台子的踏频字段在重新上电后可能一直是 0，只认踏频会
  永久卡死。功率是实打实的输出，功率达标同样算"在骑"。

## 悬浮窗：设备页那个按钮

骑台子时经常一边看视频，来回切窗口很烦，所以做了个"小飞机那种"的悬浮窗：功率/
剩余时间/心率踏频/状态浮在屏幕角落，置顶、点击穿透。

- **窗口**（`overlay.py`）：macOS 原生 `NSWindow`——无边框 + 背景 clear + `opaque=0`
  （只有文字浮着）、`level=NSFloatingWindowLevel`（置顶）、`ignoresMouseEvents`
  （点击穿透）、`collectionBehavior` 带 `FullScreenAuxiliary`（能盖在全屏视频上）、
  `activationPolicy=Accessory`（不进 Dock、不抢焦点）。用的是 `bleak` 顺带装好的
  `pyobjc`，**零新增依赖**。
- **进程**：`/api/overlay` 由服务 `Popen` 一个独立的 `overlay.py`，只读
  `/api/state`——它崩了碰不到训练循环。`start_new_session=True` 让它免受终端
  Ctrl+C 影响，服务退出时 `cleanup()` 显式收掉，不留孤儿。启动后等 0.8 秒
  `poll()` 一次：立刻退出就把退出码和日志尾巴当错误返回，前端直接弹出来。
  `_overlay_running()` 每次 `poll()`，所以进程自己没了会如实报"没开"。
- **状态在服务端**：`/api/state` 的 `overlay_running`，刷新页面/换标签页按钮都对。
- **两个坑**：
  1. `index.html` 和 `app.js` 分别缓存，浏览器可能拿新的 HTML 配旧的 JS——旧 JS
     里没有按钮的点击处理，症状是"按钮看得见、按下去毫无反应"（实测踩过）。
     现在发首页时给静态资源带上 `?v=<mtime>`，两者永远配套。
  2. 前端文件是每次请求现读的（刷新就新），**Python 是进程启动时加载的**（必须
     重启服务）。前端遇到 404 会明确提示"服务还是旧代码，请重启"，不再让人猜。

## 休息段心率：单独记一份，不进训练统计

暂停/挂起期间的心率**另存一份**，理由有两条：

- 它**不是训练负荷**。混进平均心率和区间分布会把训练数据搞脏（一场 60 分钟里休息
  16 分钟，平均心率会被拉低十几 bpm，区间分布也会多出一大块 Z1）。
- 但它**很有诊断价值**。同样是"1 小时 135W"，停下来两分钟后心率从 152 掉到 112
  和只掉到 140，说明的是两种有氧水平；而"自动继续卡住时骑手到底有没有在踩"这种
  问题，也只有休息段的心率曲线说得清（人一直在踩，心率就不会一路往下走）。

实现上就是独立的一条时间轴（骑行时钟在暂停时是冻住的，所以休息段不能挂在 trace
上）：每拍记一次，5 秒一个采样点、上限 120 点（休息很久就自动把间隔翻倍），
收尾时算 `hr_start`（停下来那一刻）/`hr_end`/`hr_min`/`hr_avg` 和
`hr_drop_60s`（停满 60 秒时掉了多少 bpm）。报告里和训练统计并排显示，互不影响。

## 自动降级的判据：探测的结论不能卡在边界差上

真机第二次翻车（用户看到"又自动切成闭环阻力了，阻力掉到 4 又爬回 20"）：

- 台子重新上电之后 ERG 有个一两分钟的整定过程（功率在 100~190W 之间晃、阻力在
  24~32 之间找），5 秒均值一度停在 150W，而目标是 140W；
- "稳但偏"的立案条件（连续 18 秒都在容差外、标准差 < 8W）被满足，程序按设计做了一次
  阶跃探测（目标 140 → 115）；
- 固件**确实跟了**：功率从 150W 掉到 **106.9W**。但 `|106.9 - 115| = 8.1`，比容差
  8.0 大了一点点——旧判据据此认定"固件不跟目标"，降级成闭环阻力（闭环控制器重新
  seed 出一个很低的档位，也就是用户看到的"阻力变成 4"，然后收敛回 20 左右）。

修法是给探测加第二条通过条件：**功率朝着新目标移动超过一半**也算"在跟"。
廉价固件"收下目标却不动"时功率几乎不动，第二条不会误判；而"跟了但过冲/欠一点"
不会再被零点几瓦的边界差判死。真机那次的数字写进了回归测试。

## 骑行台掉线：训练挂起，不结束

这条是被真机上的一次训练逼出来的，代价是一整场训练：

> 60 分钟 130W 的恒定功率训练，中途暂停休息。休息时间长，动感单车自动关机，
> 蓝牙链路断掉。用户回到设备页重新连上骑行台——**训练已经结束了**，21 分钟处
> 变成一份「提前结束」的报告，再也接不回去。

成因是两段独立的代码叠在一起：

1. 掉线（`TrainerClient._handle_disconnect` → `disconnected` 事件）在当时**什么都
   不做**，秒表继续走——没有功率数据的"休息时间"被算成了骑行；
2. 「重新连接」走的是 `_connect_trainer`，它第一步是 `_disconnect_trainer()`，
   而后者会把还没骑完的训练 `stop(reason="断开连接")` 收尾并写报告。

现在的约定，一句话：**掉线只挂起，只有明确的结束动作才会结束。**

| 动作 | 训练会怎样 |
|---|---|
| 停踩超过 15 秒 | **自动暂停**：计时冻结，踩起来自动继续（不碰骑行台） |
| 数据沉默超过 20 秒 | 同上，并按"台子不见了"处理：挂起 + 后台自动重连 |
| 后台重连 | 每 4-20 秒一轮：先按记住的地址直连，之后每轮再扫一遍广播（地址会变） |
| 骑行台断电/断链 | **挂起**：计时冻结、数据留着，`trainer_lost` 置位，提示"去重连" |
| 蓝牙半开（哑了但没报断开） | 秒表会跟着走一会儿；用户重连时同样只挂起、不结束（判据是"这场还没骑完"，不是"收到过断连事件"） |
| 重新连上骑行台（`/api/connect`） | **接回**这场训练：换设备对象，已骑时长/曲线/心率累计原样保留，仍是暂停，等用户点「继续」 |
| 点「继续」 | 重新申请控制权 + 重新下发目标（新链路的 FTMS 状态是干净的） |
| 点「结束」/ 跑满时长 | 收尾 + 写报告 |
| 点「断开」（`/api/disconnect`） | 收尾 + 写报告（原因「断开连接」），前端会先确认一次 |

实现上分三块：

- `WorkoutSession.handle_trainer_lost()`：同步方法（它由蓝牙断连回调直接调用，
  那里没有 await 的机会）。把 `running` 降为 `paused` 以冻结计时，清掉当前功率和
  观察窗口（不能拿冻结值继续积分），作废正在进行的降级探测，置 `trainer_lost`。
- `WorkoutSession.rebind_trainer()`：换 `self.trainer`、清掉"与旧链路绑定"的标定
  （闭环控制器的 `k`/档位在台子断过电之后不再可信，丢掉重来），训练本体的数据
  一律不碰。会话处于暂停时**不在这里下发指令**——控制权要重新申请、目标要重新
  下发，统一交给用户点「继续」时的 `resume()`（内部就是 `_reapply_control()`），
  那时设备才是真的就绪。会话还在跑（链路半开、断连回调没来的情况）时例外：
  立刻 `_reapply_control()` 把控制接回来，否则界面写着"原生 ERG"、实际一条指令
  都没下发过，比明确报错更难发现。
- `Server._connect_trainer()`：连接前先看有没有"还没骑完"的会话（`is_unfinished()`）。
  有就 `_disconnect_trainer(keep_session=True)`（只摘掉旧设备对象，不 stop），
  连上之后 `rebind_trainer()`。连不上也不能把挂起的训练弄丢——否则一次手滑点错
  设备就会把那场训练一起带走。

不自动"继续"是有意的：链路恢复的那一刻骑手可能根本不在车上，自己踩起来才安全。

## 诊断脚本：为什么功率压不到设定值

```bash
./run.sh --diag              # 约 4 分钟，全程保持踩踏
./run.sh --diag --sim        # 没有硬件时先看一眼输出长什么样
./run.sh --diag --quick      # 每个阶段 30 秒
```

它比训练报告多给出一列关键数据：**骑行台自己回报的阻力档位**。原生 ERG 模式下
程序一个阻力指令都没发过，所以这一列完全是固件的行为，也正是回答"它到底有没有在
调阻力"的唯一直接证据。诊断跑三个对照阶段：

| 阶段 | 做什么 | 用来排除什么 |
|---|---|---|
| **A** | 原生 ERG + 每 2 秒重发目标功率（程序现在的做法） | 基准 |
| **B** | 原生 ERG + 只在开头发一次 | 每 2 秒重发会不会打断固件自己的积分器 |
| **C** | 目标功率 +40W / −40W 阶跃 | 固件对"设定值"到底有没有伺服能力 |

跑完直接给结论，四种可能：阻力一动不动（开环查表，用闭环阻力）、阻力在动但功率
停不下来（刻度偏差或死区太大，用闭环阻力）、阶段 B 明显比 A 好（重发打断了积分器，
放宽 `POWER_KEEPALIVE_S`）、功率稳在目标附近（原生 ERG 没问题）。

**一个实测发现：回报的阻力档位和设置的阻力档位不是一个量纲。** 真机上
（FitShow FS-BLE-V3X）原生 ERG 模式下它回报的 `Resistance Level` 换算成显示值是
**1.7~3.2**，而程序用闭环控制时要设到 **15~20** 才能维持同样的功率——也就是说
固件上报的是它自己的档位刻度，不是你下发下去的那个值。所以看诊断结论时只能看
**"它动没动"**，不要拿绝对值和下发的值对比。想知道它自己声明的量程，跑
`./run.sh --diag`，开头会打印 `阻力量程(原始值)`。

**这个脚本是怎么来的**：一次真实的 60 分钟 130W 骑行里，功率在 t≈912~930 秒整整
一段**每一个采样点都精确等于 114W**——而目标是 130W。人的腿不可能这么稳，所以那
几秒里骑行台报的功率必然是它自己用「阻力 × 踏频」算出来的固定值：**阻力没动，
功率就没动**。

再看全程，这种"12 秒完全不动"的平台在原生 ERG 段占 22%，平台值散布在 76 / 114 /
116 / 118 / 119 / 124 / 126 / 129 / 131 / 134 / 163 W——一个真正在闭环的 ERG 不可能
让功率稳定地停在偏离目标 30W 的地方。也就是说：它报的"支持目标功率"是个声明，
不是保证。区别只在于"它为什么不动"，一小时的功率曲线分不出来——缺的就是**回报的
阻力档位**那一列。

## 数据存储

### 训练报告

一次训练一个文件，纯文本 JSON，在 `data/reports/` 下。之所以不是把所有报告塞进
一个大文件：报告只增不减，单文件方案每存一次都要重写全部历史，数据量一大就慢，
而且写坏一次全部丢失。

- **上限 500 份**（每份含曲线约 30KB，合计约 15MB）。超出后删除最旧的，并在日志里
  明确记一条——不静默丢用户数据。
- **写入走"临时文件 + `os.replace`"**，中途断电不会留下半截文件。
- **报告 id 来自客户端，所以做了白名单校验**：只允许字母数字和 `-`/`_`，解析完
  还要确认结果仍在报告目录内——两道保险挡住 `../` 这类目录穿越。
- **列表接口不返回功率曲线**。列表只需要几个数字，没必要把几十 KB 的轨迹传一遍。
- 目录里混进坏文件或不相关文件时会被跳过并记日志，不会让整个列表打不开。
- 报告里保留**功率、目标、阻力、踏频、心率**五列轨迹。阻力和踏频是有意留着的——
  报告是事后复盘问题的唯一依据，把这两列丢掉的话，"阻力为什么突然变了"这类问题
  就完全无从查起（真的遇到过）。
- 报告里还记录**控功率方式的切换**（什么时候、从什么切到什么、为什么）。
- 报告里还带一份**这场训练的事件表**（`events`，相对时刻 + 类型 + 说明）。
  事后复盘最缺的恰恰不是数字，而是"报告里那两段空白到底是用户按了暂停，还是
  骑行台掉线挂起了"——只看曲线和统计答不出来，只能回头问用户。上限 80 条。

### 自定义课程与设置

`data/custom_workouts.json` 和 `data/settings.json`，同样是纯文本 + 原子写入。
被改坏时程序会安全地忽略、退回默认值或空列表并留下备份，不会起不来；
读不出来的课程条目会被原样保留，不会在下次保存时被抹掉。

测试会把自己的数据写到临时目录（靠 `IBIKE_DATA_DIR`），**不会碰你的真实训练记录**。
这一条有测试专门守着。

覆盖到的关键行为（都是踩过坑之后补上的回归）：

- FTMS 编解码：`Indoor Bike Data` 位域解析（含跳位、截断、More Data 语义）、
  能力声明、指令编码逐字节校验、控制点应答（含 `Control Not Permitted`）
- 控功率两条路径的收敛性、自动降级（含"先探测取证"）、明确选了原生 ERG 时不降级
- 数据陈旧（链路还在但设备不再上报）时必须停止积分、停止调阻力，不能拿冻结值算下去
- 物理上不可能的数据帧按"没有数据"处理：骑行台报 0bpm 的心率、**0rpm 却报功率**、
  **单帧功率暴涨**。后两条是同一台固件的毛病——骑手突然停踩 / 重新踩起来的那一瞬间，
  它甩出过 273W/0rpm 和 642W/126rpm 这种帧，直接把报告的"最大功率"顶上天，
  闭环模式下还会让控制器朝错误方向拧一把。判据：不踩就不该有功率；一帧之内涨不了
  300W 以上（真冲刺只会被延迟一帧，第二帧照常采用，不抹掉真实数据）
- 暂停/断链的时间不能被算进"这一小节骑了多久"（会影响分段统计和 FTP 有效性）
- 断开骑行台不影响心率带的读数；反过来也一样
- 训练中断开连接 / 关服务时，这一场要照常落盘成报告
- 骑行台掉线只把训练**挂起**（计时冻结、不写报告），重连要能接回同一场训练；
  只有「结束」/跑满时长/显式「断开」才收尾
- 悬浮窗开关：起停子进程、进程自己挂掉要如实报"没开"、端口要传对、服务退出要一起收掉
- 停踩超过阈值自动暂停，且**停止累计当场生效**（不能等满确认期，否则报告里会
  留下十几秒 0W）；手动暂停不自动继续；坡道测试仍以「力竭」结束
- 骑行台断链 / 数据沉默后：训练挂起 **+ 后台自动重连 + 骑起来自动继续**（全程不用
  碰 HTTP 接口）；用户主动「断开」要能停掉自动重连
- 掉线时**没触发断连回调**（蓝牙半开）也不能丢训练，而且接回来之后必须重新
  申请控制权、重新下发目标（不能停在"显示在骑、其实没人管"）
- 报告 id 的目录穿越、损坏文件不影响启动、上限裁剪
- 服务端：跨站请求拦截、畸形 JSON 不 500、请求体过大如实回 413
- 前端：状态渲染、两页切换、设备块、报告里的心率与切换记录

## 关于设备兼容性（摩刻 / 动感单车）

公开渠道查不到摩刻（MOKFitness）的私有协议文档，但开源项目
[QZ (qdomyos-zwift)](https://github.com/cagnulein/qdomyos-zwift) 里没有摩刻的专用驱动，
说明它走的是**标准 FTMS**——这也是本程序默认的实现路径，理论上任何标准 FTMS
设备都能用。

需要留意的是：不少家用产品线是**动感单车**（如摩刻 S10 Ultra），这类设备的固件
有可能只实现了「设定阻力」而没有实现「设定目标功率」，或者把 `Set Target Power`
实现成开环查表。在 `auto` 模式下遇到这种情况，程序会先做一次阶跃探测取证，确认
固件确实压不到设定值之后才接管——用户不用做任何事；如果明确选了「原生 ERG」，
程序不会自作主张切换，只会提示。

遇到功率长期压不到设定值时，先跑 `./run.sh --diag` 把「骑行台回报的阻力档位」
打出来看一眼再下结论。

## 说明与已知限制

- 服务默认监听 `0.0.0.0:8765`，局域网内任何设备都能访问，**没有任何鉴权**。
  只在不担心的网络里用，别把这个端口暴露到公网。
- **只支持蓝牙 FTMS**。不支持 ANT+，也没有为任何厂商私有协议做适配。
- **实时训练中的曲线只存在内存里**——训练中途刷新页面会丢掉已经画出来的那半截
  曲线，历史报告不受影响。
- 报告里**没有 TSS / IF 这类训练负荷指标**，因为算它们需要一个另外测出来的 FTP 值，
  而程序不假装知道你真实的阈值。
- **没有训练计划日历**，不能排"下周三做 4×4"。报告只是记录，不是计划工具。
- **没有导出功能**。报告是纯文本 JSON，想要 GPX/CSV 之类的格式需要自己转。
- 界面**没有多用户**，同一时刻只维护一个训练会话（两个标签页同时操作会互相干扰，
  服务端有并发保护，但体验上不推荐）。
- **验证边界**：程序已经在一台真实骑行台（FitShow FS-BLE-V3X）上连续骑过 60 分钟，
  也在同一台台子上用真实心率带（迈金）骑完过整场：心率覆盖 100% 的秒数、无零值、
  无毛刺（相邻秒变化中位数 1bpm），RR 间期也能收到。

### 已知但暂时不修的问题

评估过、影响很小、暂时留着的问题，写在这里留个底：

- **报告列表会同步解析全部报告文件**。500 份（约 15MB）时 `GET /api/reports` 要
  0.16 秒，这段时间里 ERG 控制循环也被卡住。要治就得给每份报告加一个轻量索引文件。
- **自定速（目标功率 0）的 FTP 测试里，"功率分布"只覆盖热身段**，因为分档是按
  目标功率的百分比划的，而自由骑行段没有目标。百分比仍然合计 100%，但分母不是
  整场时长。
- **坡道测试如果在最后一级力竭**，报告会说"跑完了全部 N 级还没力竭"，和实际不符。
  多留几级余量就不会碰到。
- **坡道测试的最高一级可以到 2200W**，而恒定功率模式的上限是 2000W。
- **距离/速度是骑行台自己报的**。动感单车没有真实位移，固件通常按「踏频 × 固定齿比」
  折算（实测 30 分钟显示 12.5km），这个数只适合自己跟自己比，不要当成实际里程。
- **`scan.py --pick` 的序号没有越界检查**，输入一个不存在的编号会抛异常退出。
